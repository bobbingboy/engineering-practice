# Correctness Review Rubric

供 code-correctness skill 的 sub-agent 使用。

與 `code-quality` 的 rubric **性質不同**：那邊每一項都要求可二元判定，因為它抓的是機械式問題。correctness 不能這樣關——真正的 bug 幾乎都是「改動與既有機制的互動」，不是清單比對。

所以這裡的約束不放在「只准報清單上的項目」，而放在**證據要求**（見第 3 段）。沒有證據的推測一律不報。

---

## 1. 調查方法（先做這個，再開始找問題）

**只讀 diff 找不到 correctness bug。** 實測有效的順序：

> **先校準要回答的問題。** 不是「這個 diff 引入了什麼缺陷」，而是「**改動之後，這段程式碼對不對**」。
>
> diff 重寫過的區塊，你就擁有它——要以它自身的正確性評估，不能因為某個缺陷在改動前就存在而略過。實測漏過一次：某 commit 把 `Promise.all` 從位置索引改寫成具名解構，reviewer 逐一驗證了解構無 off-by-one 後回報「無缺陷」，卻沒看見那個它剛重寫完的批次載入裡，11 個成員只有 1 個有 per-promise catch——任一其餘成員失敗就讓整頁設定空白。以 delta 為框架時看不到，以「這段程式碼對不對」為框架時第一眼就會看到。

### 1.1 讀改動觸及的共用實作，不要只讀 diff

任何共用 lib、核心模組的函式，只要 diff 呼叫到、丟東西進去、或改變它收到的輸入形狀，就去讀它的原始碼。

> 實例：`apiGuard` 的三個 high 全部要讀 `ajax.js` 才成立——`request()` 與 `fetch()` 的 catch 都以 `err.response` 分流，interceptor 丟自訂 error 會讓底下所有 status 分支走不到。只看 diff 完全看不出來。

### 1.2 問「這個 codebase 已經有了嗎」

你在 1.1 讀共用實作時，順手回答這個問題：**diff 新寫的這件事，已經存在的程式碼是不是已經在做了？** 已經有的版本通常處理過 diff 沒想到的情況，重寫的那份幾乎必定更差。

這是本專案反覆出現的失效類別，且 `code-quality` 的 rubric 明文不管它（它只看同檔連續 5 行的重複，「跨檔案的相似性」與「看起來像可以共用」都在不報告清單裡）。所以**這裡不報就沒有人報了**。

三種常見形狀：

- **重造共用元件既有的能力** — 實例：`prompt.alert(i18n.translate(e.message))`，但 `Prompt` 本來就有 `message instanceof Error → renderError` 的路徑，會保留 `ConstraintError` 的欄位訊息且只翻譯一次；新寫的版本翻譯兩次，且 `message` 為 undefined 時彈出空白對話框。
- **自己寫 lib 已經提供的東西** — 實例：共用框架已有影像處理套件，卻自己寫了一份縮圖邏輯。
- **在呼叫端補洞而不是修共用函式** — 若同一個問題會在每個呼叫端重現，正解是修共用函式。客戶版獨有的 bug 若共用核心相同，修的也是共用核心。

### 1.3 對每個新丟出的 error／新回傳值，追到呼叫端

誰在依賴它的形狀？`.response`？`.status`？是不是 `null`？呼叫端有沒有 try/catch？

> 實例：service 新增 `throw` 之後，`applet/JobOffers/index.js` 那個沒有 try/catch 的 async IIFE 變成 unhandled rejection，畫面停在半途且無提示。

### 1.4 問「這個改動讓什麼變成可達」

原本因為別的錯誤而走不到的程式碼，可能因為這次修正而第一次真的執行。

> 實例：`i18n.translate(e)` 傳 Error 物件必拋 TypeError，整個 catch 靜默失效；改成 `e.message` 後 catch 活了，裡面的 `history.push("/logon")` 也第一次生效——任何暫時性錯誤都會把使用者踹回登入頁。

### 1.5 對每個守衛／篩選，找一個會被誤殺的合法案例

新增的檢查會不會把正常情況當異常？

> 實例：guard 攔 `text/html` 當阻擋頁，但 `fileIO.js` 把 `.htm`/`.html` 映射成 `text/html`，104 匯入的 HTML 附件也存成它——合法文件下載一律失敗。
> 實例：查詢預設套「近 7 天」時間窗，對已評核合理，對待評核（待辦）等於把逾期項目藏起來。

### 1.6 共用層的擴散

核心模組被後端服務與所有下游客製版共用；共用 lib 被本產品線以外的專案共用。公開簽章變更、行為變更（原本成功的回應改成丟錯）要指出擴散範圍。

### 1.7 兩份以上的副本是否一致

`src/util/`、`src/component/`、`src/hook/`、共用 lib 在 web / portal / expo 各有一份。diff 只改了其中一份就要報。

## 2. 失效類別（找什麼）

| 類別 | 典型形狀 |
|---|---|
| **契約破壞** | 改動讓某個既有機制的前提失效；包含「加了錯誤處理反而打斷既有的隱性耦合」（如共用 gate 的成員原本必定同時有值） |
| **新增可達性** | 原本走不到的程式碼因這次修正變成會執行，帶出未預期的副作用 |
| **合法案例被誤殺** | 守衛／篩選／預設值套用到不該套用的分支 |
| **查表落空** | 查不到回 `null` 又直接使用或寫入 `@NotNull` 欄位 |
| **邊界與空值** | `null` / 空集合 / 單元素 / 空字串 / 204 / 時區 / 全半形 / 大小寫 |
| **錯誤路徑本身** | catch 之後的狀態、unhandled rejection、錯誤訊息是否可翻譯、原始錯誤資訊是否遺失 |
| **並行與時序** | 註冊順序、初始化時機、race、in-flight 重複請求 |
| **資源無界** | 無淘汰的快取、無上限的查詢、空條件全表 |
| **重造已有的輪子** | 共用元件／lib／既有 helper 已經在做這件事，diff 又寫了一份比較差的（見 1.2） |
| **改寫但未修復** | diff 重寫了一個區塊，卻原封保留該區塊既有的缺陷。缺陷比改動更早存在**不是**略過的理由——重寫了就擁有它 |

簡化與效率也一併看，但 correctness 與 reuse 優先——那兩類放在最後，且不得排擠前兩者的篇幅。

## 3. 證據要求（這是本 rubric 的主要約束）

每一筆 finding 必須同時具備：

1. **明確的「檔案:行號」**
2. **觸發條件** — 什麼輸入／狀態／時序會讓它發生。寫得出具體情境才報，寫不出來就是推測
3. **後果** — 使用者或資料實際會怎樣
4. **佐證** — 你讀了哪個檔案（或哪一行）才確認這條成立。若只憑 diff 推斷而未查證，**不要報**

**結構性缺陷的例外**：死碼、重造已有的輪子、缺少錯誤隔離這幾類，依定義就沒有 runtime 觸發條件——它們的問題不在「某個輸入會爆炸」。這類以「**什麼情況下會出事**」或「**它讓什麼變得更差**」代替第 2 點，其餘三點照舊。

**不要因為「沒有觸發條件」就把它降級成觀察或直接不報。** 實測踩過：reviewer 找到一支零呼叫者的死碼 service 函式，卻以「has no trigger condition and predates the commit」為由主動排除，等於用證據要求把自己找到的東西丟掉。證據要求是用來擋推測的，不是用來擋結構性問題的。

**一律不報**：

- 「可能會…」「建議評估…」「考慮…」這類沒有觸發條件的推測
- 從未讀過實作就斷言某個共用函式的行為
- 風格偏好、命名、未使用 import（那是 `code-quality` 的範圍）
- 質疑 prompt 中「設計脈絡」段已載明的決策
- 落在 diff 行號範圍外的既有程式碼（除非它正是 diff 破壞的那個機制，此時要明確說明關聯）

## 4. 嚴重度

| 級別 | 判準 |
|---|---|
| **critical** | 資料遺失／毀損、安全邊界被突破、全站不可用 |
| **high** | 明確會發生的錯誤行為，且使用者無法自行繞過（如失去重新登入路徑） |
| **medium** | 明確會發生但影響侷限，或有繞過方式 |
| **low** | 邊界情境、診斷能力受損、測試缺口 |

**自行判定，不要沿用你在別處看到的標籤。** 觸發條件愈普遍、使用者愈無法自救，級別愈高。

## 5. 常見的自我開脫

審查自己或另一個 agent 寫的程式碼時，這些念頭會讓你放過真正的問題。

| 開脫 | 事實 |
|---|---|
| 「AI 產的程式碼應該沒問題」 | AI 產的程式碼需要**更多**檢查而非更少。它自信、看起來合理，錯的時候也是。 |
| 「我剛寫的，我知道它是對的」 | 作者對自己的假設是盲的。這正是本 skill 要派獨立 sub-agent 的原因。 |
| 「測試過了，應該沒事」 | 測試是必要不充分。實例：`apiGuard` 的測試全綠，但沒有一條涵蓋 `fetch()` 路徑，而那正是影響最大的呼叫端。 |
| 「它能動就好」 | 能動但打斷了既有機制的程式碼，故障會出現在遠離成因的地方——那是最貴的一種。 |
| 「這只是小改動」 | 本次三個 high 全部來自四行以內的改動。改動大小與後果無關。 |
| 「之後再清」 | 之後不會來。 |

---

## 6. 輸出格式

```
[severity: critical|high|medium|low] [category] 檔案:行號
觸發條件 → 後果。（佐證：讀了什麼確認的）
```

最嚴重的排最前面。無發現則明確說「無」。

**把重點放前面，不要把真問題埋在一堆小事底下。** 若你有一個結構性問題與十個枝節，那個結構性問題**就是**這次審查的全部——幾筆高信心的 finding 勝過一長串清單。實測有過一次吐 11 筆、真正要緊的兩筆混在中間的情況。

同一個根因造成的多個後果，**合併成一筆**並列出它有幾個後果，不要拆成多筆——拆開會讓人誤以為是多個獨立問題。
