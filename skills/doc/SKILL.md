# Doc Co-Authoring

協助使用者在 Obsidian 知識庫中撰寫技術文件的三階段工作流程。

## Obsidian 知識庫結構

本庫採 **LLM-wiki 模式**：`index.md` 是內容目錄、`log.md` 是時間線、`sources/` 放只讀原始素材、知識頁與原始素材分離。詳見 `knowledge/CLAUDE.md` 的「維護流程」。

```
knowledge/
├── _templates/           # 筆記模板
├── projects/<project>/   # 專案專屬知識頁
├── topics/               # 通用技術知識頁
├── sources/              # 只讀原始素材（不在本 skill 產出範圍）
├── index.md              # 內容目錄：每篇知識頁一行摘要
└── log.md                # 時間線：append-only 的 ingest/lint 紀錄
```

**本 skill 只產出知識頁**（`projects/` 或 `topics/`），不寫 `sources/`（那是原始輸入，只讀）。每完成一篇知識頁，必須執行下方「完成收尾」的 ingest 步驟，否則 `index.md` / `log.md` 會立刻過時。

### 模板類型

| 類型 | 用途 | 段落結構 |
|------|------|----------|
| feature | 功能文件 | 概述、使用方式、API、備註 |
| lesson | 經驗教訓 | 背景、問題、原因分析、解決方式、教訓 |
| troubleshooting | 問題排查 | 問題描述、判斷方式、排查步驟、解決方式 |
| deployment | 部署流程 | 部署項目、前置作業、部署步驟、驗證 |

### Frontmatter 格式

```yaml
---
title: 標題
type: feature | lesson | troubleshooting | deployment
date: YYYY-MM-DD
project: (僅專案文件需要)
tags: []
related: []
---
```

### 分類原則

判斷放 `projects/` 還是 `topics/`：**離開該專案後，這篇還有用嗎？**
- 有用 → `topics/`
- 沒用 → `projects/<project>/`

## 工作流程

開始時先向使用者簡介三個階段，詢問是否要使用此流程或自由撰寫。若使用者接受，進入 Stage 1。

### Stage 1：蒐集脈絡

目標：拉齊雙方的資訊落差，為後續撰寫打好基礎。

**初始問題**（一次問完，使用者可以用簡短方式回答）：

1. 這篇文件的**類型**是什麼？（feature / lesson / troubleshooting / deployment）
2. 主要**讀者**是誰？
3. 希望讀者看完後能獲得什麼？
4. 屬於哪個**專案**，還是通用技術主題？（決定存放路徑）
5. 有沒有**相關的現成文件可以提供**？（郵件、log、規格、外部文章等——若有，會綜述進文件並存進 `sources/` 留底。沒有也沒關係，很多筆記純從討論寫成。）
6. 其他需要知道的脈絡？

根據回答決定：模板類型、檔案路徑（`projects/<project>/` 或 `topics/`）、檔名、以及是否有 `sources/` 素材。

> 第 5 題是**請使用者提供**，不是模型自己去取得。使用者沒有就跳過；**不要**主動去 fetch 網址、下載郵件或爬取內容來湊 source。

**資訊傾倒（Info Dump）**

鼓勵使用者把所有相關脈絡一次倒出來，不需要整理格式：
- 問題背景、技術架構
- 團隊討論、相關文件
- 嘗試過的方案、為什麼某些方案不可行
- 時程壓力、技術限制

**釐清問題**

使用者傾倒完畢後，根據資訊缺口提出 5-10 個編號問題。使用者可以用簡短方式回答（如「1: 對、2: 不確定、3: 參考 XX 文件」）。

**結束條件**：當你能問出邊界情境和取捨問題（而非基礎問題）時，代表脈絡已足夠。詢問使用者是否準備好進入撰寫階段。

### Stage 2：逐段精煉

目標：逐段建構文件，每段經過腦力激盪、篩選、撰寫、修改。

**建立檔案骨架**

根據 Stage 1 決定的模板類型，用 Write 工具建立檔案。自動產生 frontmatter（填入 title、type、date、project、tags），段落使用模板結構，內容先放 `[待撰寫]` 佔位。

從最多未知數的段落開始（通常是核心內容段落），摘要段落留到最後。

**每個段落的處理流程：**

1. **釐清**：針對該段落提出 3-5 個問題，確認要涵蓋什麼
2. **腦力激盪**：列出 5-15 個可能納入的要點，包含使用者可能遺忘的脈絡與角度
3. **篩選**：請使用者指出保留、移除、合併哪些（如「保留 1,4,7」「移除 3（跟 1 重複）」）。若使用者給自由格式回饋，解讀其意圖後繼續
4. **缺口檢查**：確認是否遺漏重要內容
5. **撰寫**：用 Edit 工具將佔位文字替換為正式內容
6. **迭代修改**：使用者提出修改意見，用 Edit 工具做局部修改（不要重印整篇）。持續到使用者滿意為止

第一次撰寫段落時提醒使用者：**請用文字描述要改什麼，而不是自己去改檔案**。這樣能幫助學習使用者的風格，讓後續段落寫得更準。例如：「第三段太冗長，精簡一點」或「移除 XX 項目，已經在 YY 涵蓋了」。

**品質把關**：連續 3 次迭代沒有實質修改時，問使用者「有沒有什麼可以刪掉而不損失重要資訊的？」

**完成度 80% 時**：重讀整篇文件，檢查段落間的流暢度、一致性、重複或矛盾，以及是否每句話都有份量。

### Stage 3：讀者測試

目標：用沒有對話脈絡的 sub-agent 測試文件，找出作者的盲點。

**步驟 1：預測讀者問題**

列出 5-10 個讀者在看到這篇文件時可能會問的問題。

**步驟 2：Sub-Agent 測試**

用 Agent 工具生成 sub-agent，只給它文件內容和問題，不給任何對話脈絡。Prompt 範例：

```
以下是一篇技術文件，請閱讀後回答問題。對每個問題請提供：
1. 你的回答
2. 文件中是否有不清楚或模糊的地方
3. 文件假設讀者已經知道哪些背景知識

[文件內容]

問題：
[問題列表]
```

**步驟 3：額外檢查**

再用 sub-agent 檢查：模糊之處、前後矛盾、隱含假設。

**步驟 4：修復**

彙整 Reader Agent 發現的問題，回到 Stage 2 修復。重複直到 Reader Agent 能正確回答所有問題。

## 完成收尾（ingest 步驟，必做）

文件通過讀者測試後，依序完成以下 ingest 步驟。**前四步不可省**，否則 `index.md` / `log.md` 會過時、失去 LLM-wiki 模式的價值（詳見 `knowledge/CLAUDE.md`）。

1. **建雙向 backlink**（強制，非「建議」）：
   - 在文件尾加 `## 相關` 區，用 `[[note-name]]` 連到**真實相關**的知識頁，並到對方頁面補回連。
   - 同步填 frontmatter 的 `related` 欄位。
   - **寧缺勿濫**：只連有實質關聯的（同功能、同 bug 群、互補概念）。沒有真實關聯就留白，**不要為了連而連**——萬用方法論式的假邊會讓 graph 變糊。
   - 程式碼路徑、OpenSpec 路徑等「非筆記」連結，請用 `## 相關檔案` / `## 相關連結`，與 `## 相關`（筆記↔筆記）分開。
2. **更新 `index.md`**：在對應分類（topics 子類 / projects/<project>）加一行「`[[note]]` — 一句摘要」。
3. **append `log.md`**：在時間線底部加 `## [YYYY-MM-DD] ingest | 標題`（日期取今天）。
4. 提醒使用者自己做最後一次通讀，確認事實、連結、技術細節正確。

> **歸檔 `sources/`（承接 Stage 1 第 5 題）**：若使用者**提供了**現成素材（郵件、log、規格、外部文章），或**指定一個網址**要參考，把它存進 `sources/`：
> - **存快照不只存 URL**（連結會死）：存全文 markdown，或至少「關鍵摘錄 + URL + 擷取日期」。
> - 加 provenance frontmatter：`type: source`、`origin: web|email|user-file`、`url`（web 才有）、`accessed: YYYY-MM-DD`。
> - 在知識頁開頭註明「本文綜述自 `[[sources/xxx]]`」，並在 `index.md` 的 sources 區登記。
> 界線：歸檔由**使用者主導**——使用者提供或指定的就取得後存底；但**不要**自己主動 fetch/爬取內容來囤積、湊 source。使用者沒提供、或這篇純從討論寫成（很多 lesson 即如此），就沒有 source，跳過即可。詳見 `knowledge/CLAUDE.md` 的「sources/：外部素材歸檔」。

> **驗 wikilink 的陷阱**：Obsidian 不解析 code fence（```）內的 `[[ ]]`。若用 `grep '\[\['` 自我檢查連結，會把 bash 的 `[[ ]]` 測試語法誤報為連結——驗證時要避開 fence，或請使用者開 graph view 確認。

## 撰寫原則

- 所有內容使用繁體中文，技術專有名詞保留英文
- 段落之間用 `---` 分隔時要謹慎，Obsidian 中 `---` 在文件開頭會被解讀為 frontmatter
- 保持精練，每句話都要有資訊量，避免空泛的描述
