## 背景

設計多個類似的模組時，常見的設計直覺是：「這個跟其他不一樣，是不是應該對齊？」

這個直覺背後實際上混合了**兩種完全不同的動機**：

- **A. 主動架構整潔** — 為了讓整個元件樹更乾淨、組織更明確，主動套用某個模式
- **B. 被動消除痛點** — 因為觀察到具體的維護痛點（重複、難追、混亂），事後重構

兩種動機都正當，但**用在錯的地方會變成 over-engineering 的偽裝**。這份筆記整理判斷兩者邊界的辯證框架，供未來設計決策時參考。

## 問題

當你看到「N 個模組裡，K 個用了模式 X，N-K 個沒用」，要不要把剩下 N-K 個也對齊到 X？

直覺答案常常是「對齊比較好」，但這個直覺需要被挑戰，因為它可能來自：

1. 美學偏好（「看起來統一」）
2. 一致性焦慮（「為什麼這個不一樣」）
3. 想像中的未來收益（「以後加新功能會更輕鬆」）

這三種都**不是好的重構動機**——它們未必對應到實際痛點。

## 原因分析

### 為什麼「對齊」常常是 over-engineering 的偽裝

#### 1. 「整潔」沒有可量化的標準

「乾淨」「整潔」是主觀感受。如果一個模組現在的 state 散落程度不嚴重、props drilling 不深、修改一處不需要動三處，那加上更高層的抽象（Provider、HOC、Layer 等）換到的「整潔感」邊際收益可能很小，但成本是實在的。

判斷方式：**能不能描述「不對齊」造成什麼具體問題？**

- 可以 → 是真的痛點，對齊有意義
- 不能，只是「感覺不一致」→ 美學偏好，應該保留現狀

#### 2. 抽象不是免費的

加一層抽象（Provider、Context、自訂 hook、基底類別等）的具體成本：

- 新增檔案、樣板程式碼
- 跨子元件的 props → hook / context 轉換
- 多一層 component tree 的 debug 難度
- 新進工程師讀程式碼時多一層間接性（「這個 state 在哪裡？答：在 X 層」比「在這個檔案行 N」更難追蹤）
- 對應的測試成本

如果痛點不存在，這些成本就是淨損失。

#### 3. Rule of Three 的適用範圍與限制

Martin Fowler 的 Rule of Three：發現第三次重複時才抽象。這個原則對「DRY 場景」非常適用，但**對「組織結構場景」需要重新評估**：

- **DRY 場景**：同樣的邏輯被寫了 N 次 → 抽出共用函式。Rule of Three 適用。
- **組織結構場景**：同樣的「狀態管理位置」散落在不同層級（有些放 component state、有些放 context、有些用 redux）→ 統一到一個層級。這時 Rule of Three 不是好標準，因為「組織不一致」本身就是痛點，不必等到第三次出現。

關鍵差異：DRY 是關於「程式碼重複」，組織結構是關於「找東西的可預期性」。後者的痛點是漸進累積的，不是離散的「第幾次」。

#### 4. 「主動架構整潔」何時成立、何時不成立

**成立的條件**：

- 已經有實際的對照組驗證這個模式可行（codebase 內已有 2+ 個成功案例）
- 該模式對應的「問題類別」確實會在這類模組中出現（即使現在還沒嚴重）
- 主動套用的成本（重構 + 後續維護）< 等到痛點出現再做的成本

**不成立的條件**：

- 只是「想像中未來會比較乾淨」，沒有具體場景支持
- 該模組目前完全沒有跨層共用、props drilling、dialog 散落等問題
- 套用後會引入新的隱性教條（見下一點）

#### 5. 強制對齊會把工具變教條

當一個模式被廣泛套用後，會建立隱性約束：「這類模組就該用這個模式」。

舉例：如果三個 management applet 都用 ActionsProvider 模式，第四個新建的小 applet（只有 list、沒批次、沒 dialog）會被迫加 Provider 才能「對齊慣例」。這時 Provider 從**工具**變成**教條**——它不再是「適合時使用」的選擇，而是「不用會被質疑」的義務。

慣例的價值在於「可預期」，但代價是「失去工具選擇權」。對齊的範圍越大，這個代價越高。

### 反向：何時「對齊」確實是好設計

如果以下條件成立，「主動對齊」就不是 over-engineering：

1. **有 2+ 個正解案例** — 不是猜想，而是觀察到 codebase 內已有成功運作的對照組
2. **不對齊的模組有跡象暴露出該模式對應的問題** — 例如：state 跨層共用困難、dialog 邏輯分散在多處、新增功能要動很多檔
3. **對齊成本可控** — 不會牽動太多無關範圍
4. **對齊後不會建立教條** — 有明確邊界說「Provider 只在 X 條件下用」，避免變強制慣例

### 案例對照（2026-05）

4 個 management applet 的 Provider 設計：

| Applet | 設計 | 評估 |
|--------|------|------|
| CandidateManagement | Provider 包整個頁面，不條件渲染 | 正解 |
| JobOfferManagement | Provider 包整個頁面，不條件渲染 | 正解（主動採用，沒有可見痛點驅動） |
| InterviewAppraisal | Provider 只包 detail pane，條件渲染 | outlier |
| RequisitionPipeline | Provider 只包 detail pane，條件渲染 | outlier |

爭議點是「該不該把 4 個都對齊」。

**JobOfferManagement 是「主動架構整潔」動機的活證據**——當時沒有可見痛點，但採用了 Provider 模式，且運作良好。這推翻了「沒痛點不該動」的單一原則。

但要注意：**「JobOfferManagement 成功了」不能反過來證明「凡是主動對齊都成功」**。它只證明「在這個 codebase、這類 management applet、有 dialog 與批次操作的場景下，主動套用 Provider 是好選擇」。換個場景（譬如純展示頁面、無 dialog、無批次），主動加 Provider 仍可能是 over-engineering。

## 解決方式

### 評估「該不該對齊」的 checklist

面對「N 個模組裡 K 個用了模式 X，要不要對齊」的決策時，依序問：

**第一層：辨識動機**

1. 我的動機是「具體痛點驅動」還是「美學偏好驅動」？
2. 能不能用一句話描述「不對齊」造成的問題？
3. 如果一個新進工程師接手這 N 個模組，他會主動問「為什麼不一致」嗎？還是不會注意？

如果第三題答「不會注意」，動機很可能是美學偏好，需要更謹慎。

**第二層：評估成本**

4. 對齊需要動多少檔案？是否會跨多個 PR？
5. 對齊後測試需不需要重寫？
6. 是否會引入新的間接層（讀程式碼時要多展開一層）？
7. 抽象之後的「集中點」會變多大？（譬如 Provider 內塞 30 個 state 也很糟）

**第三層：評估收益**

8. 這個模式在 codebase 內已有幾個成功案例？（< 2 個是「實驗」，≥ 2 個是「慣例」）
9. 對齊後是否有可量化的得益？（譬如：消除 N 個重複 state、減少 K 處 props drilling）
10. 對齊後會不會建立新的教條？有沒有明確邊界說「這個模式只在 X 條件下用」？

**第四層：評估時機**

11. 這個對齊跟當前手上的工作有沒有關聯？是「順便」還是「綁裝」？
12. 拆成獨立 commit/change 是否更合適？

### 決策矩陣

| 動機 | 已有正解案例 | 有具體痛點 | 建議 |
|------|------------|----------|------|
| 美學一致性 | 是 | 否 | **不動**（這是 over-engineering） |
| 美學一致性 | 是 | 是 | 動（痛點是真實驅動，「對齊」只是執行手段） |
| 想像未來收益 | 否 | 否 | **不動**（speculative refactoring） |
| 想像未來收益 | 是 | 否 | 看 codebase 內慣例的成熟度——成熟可動，實驗階段不動 |
| 主動架構整潔 | 否 | 否 | **不動**（沒對照組就不要實驗在現有 codebase 上） |
| 主動架構整潔 | 是 | 否 | 可動，但要承擔「建立新教條」的長期成本 |
| 痛點驅動 | 任意 | 是 | 動 |

## 教訓

### 主要 takeaways

1. **「為什麼這個跟其他不一樣」這個直覺要被挑戰**。它可能來自痛點，也可能來自美學焦慮。先辨識動機再決定。

2. **「主動架構整潔」是個合法但容易被濫用的動機**。當有 2+ 個成功案例支撐時，它是合理的；當只是個人偏好時，它是 over-engineering。

3. **Rule of Three 不是萬能標準**。它適用於 DRY 場景（程式碼重複），但對組織結構場景（可預期性、找東西的成本）需要其他標準。

4. **抽象不是免費的**。每次新增一層 Provider/Context/Layer，都要付出檔案、樣板、間接性、測試的代價。痛點不存在時，這些代價是淨損失。

5. **慣例是參考，不是教條**。對齊的範圍越大，「不對齊會被質疑」的隱性壓力就越大，這會剝奪未來的工具選擇權。要主動劃定邊界。

6. **拆 commit 的價值**：當一個架構修正跟業務 bug 修復混在一起時，拆成兩個獨立 change 通常是對的——架構決策可獨立 review、獨立 rollback。

### 反思工具

每次想做「對齊式重構」前，問自己：

- 痛點清單：列出至少 3 個具體痛點。寫不出來 → 動機是美學。
- 假想質疑：想像一個資深工程師看到這個 PR，他會不會問「為什麼現在做這個？」。會 → 動機不夠強。
- 範圍邊界：明確寫出「這個模式適用於 X，不適用於 Y」。寫不出來 → 慣例會變教條。

### 應用範例

**情境**：發現 codebase 內 React 元件有些用 useState、有些用 useReducer，想統一。

- 痛點清單：能寫嗎？「現在的混合讓修改 state 邏輯時要先猜哪種」——這算痛點，但不嚴重。
- 假想質疑：「為什麼現在統一？」——沒有特別理由。
- 範圍邊界：「複雜 state 用 useReducer，簡單用 useState」——這個邊界本來就清楚，強制統一反而破壞。

→ **不動**。這是美學偏好。

**情境**：發現 codebase 內 5 個頁面都自己實作了 Tab 切換邏輯，每個都不一樣。

- 痛點清單：「修改 tab 邏輯要動 5 處」「視覺不一致」「測試重複」——3 個痛點。
- 假想質疑：「為什麼現在做？」——「正在加第 6 個頁面，不想再寫一次」——強動機。
- 範圍邊界：「所有需要 tab 切換的頁面都用 SharedTabs」——清楚。

→ **動**。這是真實 DRY + 一致性需求。

## Origin

這份筆記源自 2026-05-13 一次拒絕函批次寄送 bug 修復過程的設計討論。

當時的爭議是：發現 RequisitionPipeline 的 ActionsProvider 設計不夠廣泛（只 wrap detail pane），是否要連帶把 InterviewAppraisal、JobOfferManagement 也一起對齊到 CandidateManagement 的模式（Provider 包整個頁面）。

我以為「JobOfferManagement 沒 Provider」，論證「沒痛點不該動」，挑戰「主動架構整潔」這個動機。後來發現 JobOfferActionsProvider 其實已經存在且運作良好——這個 applet 就是主動採用、沒可見痛點驅動的成功案例，反證了我的單一原則。

從這個對話得到的辯證框架：**動機（美學 vs 痛點）× 對照組（有 vs 無）× 時機（單獨 vs 綁裝）三個維度交叉，才能正確判斷對齊式重構該不該做**。單一原則（譬如「YAGNI」「Rule of Three」「DRY」）都不足以涵蓋所有情境。
