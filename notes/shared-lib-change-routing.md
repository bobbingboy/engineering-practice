## 這份文件解決什麼

需要一個 `shared-lib` 沒有提供的行為時，要改 lib，還是在自己的專案裡解決？

這個判斷過去憑直覺，結果是**兩種相反的錯誤都會發生**：該進 lib 的東西留在產品端（其他產品永遠拿不到），或不該進 lib 的東西被塞進去（所有人承擔別人的政策）。

這份文件給的是**判斷路由**，不是評分表：走完之後應該能說出「這件事屬於哪裡、為什麼、現在該做什麼」。它不決定該不該做某個功能，只決定**做出來的東西該住在哪裡**。

前置規範（改 lib 前要滿足的流程條件：維護者確認影響範圍、改動進上游、測試涵蓋等）見 `主專案/CLAUDE.md` 的「共用 lib 的修改門檻」。那份講的是**門檻**，這份講的是**歸屬**——先用這份判斷該不該進 lib，再用那份確認能不能動手。

## 前提：散佈機制決定了判準的權重

`shared-lib` 是 **vendored** 進各專案的——原始碼實體存在自己的 repo 裡（`src/lib/shared-lib/`）、跟著專案一起 commit，不是從套件庫安裝的相依。因此它可以被直接編輯，也因此本地編輯會在下次更新時被覆蓋。

實際的散佈機制是：**lib owner 直接對各專案 repo 提交，各專案在 pull 時取得新版本**。

使用端**不能選擇性接收或延後**某次更新：owner 提交後，pull 下來就是新版本，沒有挑選的餘地。這一點是後面所有風險論證的前提。

> **這個前提哪天會失效**：若 lib owner 導入版本管理（semver、tag、可釘版本），選擇性接收就成為可能，接收端也就有了審查與延後的能力。屆時〈行為性變更要降級成 opt-in〉的必要性會下降，那一節要回來改寫。在那之前，按「不能拒絕」處理。

## 判斷路由

先問第零層，再走三層。輸出是一條**路由**與其理由，不是分數。

### 第零層：有沒有擴充點

> 這個需求能不能用 lib **已經公開的擴充點**達成？（如 `ajax.interceptors`）

能 → 就這樣做，把實作寫在自己的 `src/util/`、在進入點註冊。**這不是妥協方案**：它不需要承擔後面三層要處理的任何風險，而且下次 pull 不會被蓋掉。

**但擴充點必須真的是為這件事開的。** 判準：這個擴充點被公開出來的**意圖**，是否涵蓋我們要做的事——相同，或是我們意圖的超集。

`ajax.interceptors` 存在的意圖是「在請求／回應流程中插入橫切處理」，攔截一個不合法的回應正落在裡面；但同一個 hook 若被拿來重寫商業邏輯、改寫特定端點的資料、或補一個 lib 根本沒打算提供的能力，那是**濫用**——只是把違建蓋在合法的地基上。

反面訊號：實作裡開始判斷特定 URL、特定產品的欄位、或需要理解某支 API 的語意。那代表你在用一個通用接口做專用的事，該退回第一層重新判斷歸屬，而不是因為「反正有接口可以掛」就塞進去。

濫用擴充點比直接改 lib 更難發現：改 lib 至少會在下次 pull 時衝突，掛在 hook 上的東西可以安靜地活很久。

這一步排在最前面，是因為它是最常被跳過的一步（見〈為什麼這個判斷容易做錯〉第一條）。看到 lib 有缺陷時，就地修最直覺，但那是最難回收的路徑。

**走了擴充點，歸屬判斷仍然要做。** 擴充點解決的是「我們現在怎麼辦」，不是「這件事該屬於誰」——若第一層判定為契約，那筆向上游提案的債照樣欠著。

### 第一層：歸屬（否決性）

> 這個行為是在描述 lib 的**契約**，還是產品的**政策**？

判斷法：**有沒有任何產品可以合理地選另一邊？**

沒有 → 契約。講得出一個會想要相反行為的產品 → 政策。

（不要問「這該不該是預設值」——預設值蘊含可覆寫，於是「附了合理預設的政策」也會通過測試，分不出要分的兩件事。）

| | 例 | 歸屬 |
| --- | --- | --- |
| 契約 | 「HTML body 不是合法的 JSON API 回應」——換到任何產品都成立 | lib |
| 政策 | 「401 要導去 `/session-expired`」——別的產品可能想跳登入框 | 產品端 |

**落在「政策」就結案**：後兩層再強也不進 lib。這一層是否決，不是加分項——不可以用其他層的強度把它蓋過去。

### 第二層：壓力（值不值得推上去）

留在產品端要付出多少代價？兩個因素：**要在幾個地方各裝一次**，以及**漏裝時會怎樣**——是大聲失敗（啟動就爆，馬上發現）還是無聲出錯（只在特定條件下才發作，會潛伏）。

實務讀法：**漏裝會無聲出錯就當高；會立刻炸就當低**，除非要裝的地方多到荒謬。無聲那一軸的權重遠大於次數。

不必糾結界線。高與低都會走到上游，差別只在要不要同時自己迴避——**真正決定路徑的是第三層**。

### 第三層：時機（誰做、什麼時候做）

- 影響範圍現在稽核得了嗎？
- 上游的回應速度跟得上眼前的需求嗎？
- 有沒有正在燒的故障？

**這一層完全不影響歸屬結論**，只影響路徑與時程。把「現在不方便改 lib」記成「這本來就該放產品端」是最常見的誤記——它會讓一個暫時的迴避方案永久留在錯誤的位置，而且沒有人記得它原本該搬走。

### 四種路由

| 歸屬 | 壓力 | 時機 | 現在要做的事 |
| --- | --- | --- | --- |
| 契約 | 高 | 可行 | **改 lib**（形狀見下節） |
| 契約 | 高 | 不可行 | **產品端迴避 ＋ 向上游提案**——兩者是同一條路由的兩半，提案不可省 |
| 契約 | 低 | — | **提報上游**。不急，也不需要為此自己先做一套迴避（要做也可以，只是不划算） |
| 政策 | — | — | **產品端**，結案 |

**最後一欄是「現在要做的事」，不是歸屬。** 前三列的歸屬都是 lib——第 2 列寫「產品端迴避」指的是暫時的落腳處，不是這件事從此屬於產品端。這個區別就是第三層那段警告的內容。

討論時要能說出走的是哪一條、以及每一層的理由。說不出理由代表判斷還沒做完。

## 行為性變更要降級成 opt-in

這是本文最可操作的一條。

**新增能力（additive / opt-in）**：提供一個函式、helper、可選的 hook。push 下去不影響任何人，用不用由各產品自己決定。

**改變既有行為（behavioural）**：改變既有函式的回傳值或例外行為。push 下去所有產品立刻承受。

在**沒有版本號、沒有更新通知**的散佈機制下，行為性變更的風險是：

> lib owner push → 各專案 pull → 某個依賴舊行為的產品**靜默壞掉**，而且沒有任何線索指向 lib 更新。

接收端沒有 changelog 可看、沒有版本可釘、無從審查。而 lib owner 的稽核範圍雖然遠大於單一產品，也未必涵蓋所有使用端的**執行期**行為——靜態搜尋「有沒有人依賴這個行為」不是充分證據。

**所以：在無版本機制下，行為性變更應主動降級成 opt-in 的新增性變更。**

作法是把能力放進 lib，但預設不啟用，由各產品在自己的進入點決定是否安裝。這樣傳播（owner push 一次全拿得到）與安全（沒啟用的產品行為完全不變）同時成立，也把「這個產品需不需要」的判斷留在唯一有能力判斷的人手上。

### opt-in 沒有兌現契約——它只是把風險換成時間

這裡有一個必須講清楚的張力：如果某件事真的是**契約**（＝正確性問題），那預設不啟用意味著**沒有 opt-in 的產品繼續帶著缺陷**，而他們正是最不會知道有這回事的人。opt-in 保住了安全，卻沒有兌現契約。

所以 opt-in 是**遷移的第一步，不是終點**。完整路徑是：

1. 進 lib，預設關閉，我們自己先啟用
2. 觀察一段時間，確認沒有預期外的影響
3. **由 lib owner 把預設翻成開啟**，或直接內建
4. 若一直沒翻正，那是一筆未結的債，不是完成狀態

送出 opt-in 提案時就要講明第 3 步的意圖，否則它會永遠停在第 1 步。

**例外：不該降級的情況。** 資安修補、以及「舊行為在任何解讀下都是錯的」純 bug（不是行為差異，是壞掉），不適用降級——那種情況下 opt-in 等於讓多數產品維持在壞掉的狀態。判斷法：**有沒有任何產品可能合理地依賴舊行為？**完全沒有，就直接改。

## 什麼情況明確不該進 lib

判準講正面容易被過度套用，以下四種情況直接停在產品端。

**行為屬於產品政策。** 第一層的反面。「session 過期後要導去哪裡」「錯誤訊息用什麼語氣」——這些換一個產品就該有不同答案，放進 lib 等於替別人做決定。

**看得到的需求只有一兩個產品，或動機只是消除重複。** 重複不等於共用：同樣的程式碼出現在兩個地方，可能是巧合而非共同契約。進了 lib，所有產品都要承擔它的維護與風險，而只有少數人得到好處。判準問的是「這是不是跨產品的契約」，不是「這段有沒有重複」。

注意這裡的方向：**看不到其他產品的需求，不足以斷言「只有我們需要」**——視野限制在兩個方向都成立。所以這一條只在「連我們自己都只有一兩處要用」時才適用；若判斷依據是「別人好像沒在用」，那就是回到了第一層，該問的是契約還是政策。

**需求還在變動。** lib 沒有版本可釘，改一次所有產品立刻承受。把還在調整的東西放進去，等於反覆推行為性變更。先在產品端養到穩定，再談歸屬。

**緊急止血。** 止血方案的本質是暫時的，該走〈四種路由〉第二列——產品端迴避、同時提案。用急迫當理由塞進 lib，是把最難回收的路徑留給最沒時間思考的時刻。

## 為什麼不跨層加總

一個很自然的念頭是把判準列成清單、各給權重、算出總分、訂一個及格線。**反對的不是「做出高低判斷」**（第二層就是），而是**跨層加總**與**及格線**。三個理由。

**判準之間不可通約。** 歸屬若落在「政策」，其他判準全中也不該進 lib——那不是權重低，是**否決**。塞進加總等於允許用數量淹沒一個本質判斷。

**總分製造假精確。** 「這條算 3 分還 4 分」本身就是判斷，包一層數字之後反而看起來像客觀結論，而且會被反過來湊分數。（第二層的「高／低」同樣是判斷、也同樣不精確——差別在於它不會被拿去加總，也不會有人為了湊及格線去調整它。）

**清單裡混了三種不同的問題。** 「該屬於誰」「有多痛」「現在能不能做」是三個獨立問題，混在一起算總分，得出的數字不對應任何真實的東西。把它們拆開，就是〈判斷路由〉的三層結構——**三層的由來就是這個**。

## 為什麼這個判斷容易做錯

以下五種失敗模式。前三種在 2026-07-30 那次判斷中**實際發生過**（標「✗ 犯過」），後兩種當時沒有發生，但都是差一步的距離。

### 略過「有沒有擴充點」直接動手改 lib ✗ 犯過

看到 lib 有明顯缺陷時，就地修最直覺、diff 也最短。那次的第一版實作直接改了 vendored 的 `core/ajax.js`，四個模組各改一份，**完全沒有先問 `ajax.interceptors` 能不能達成同樣效果**——而那個擴充點是 lib 本來就公開的。發現後全數還原重做。

就地修看起來最短，但它是**最難回收**的一種：下次 pull 就被蓋掉，而且不會有人注意到。

### 用自己的搜尋結果代替影響範圍稽核 ✗ 犯過

那次曾根據本機的全域搜尋，斷言「沒有任何產品依賴 HTML 回應」。這個結論**必須收回**——本機只有自己負責的專案，其他負責人的專案不在裡面。

grep 沒有命中，只代表看得到的範圍裡沒有命中。

### 把事實搞錯，導致整組權重算錯 ✗ 犯過

那次一度認定 lib「沒有散佈機制」，並據此判斷「改 lib 的成本極高，因為要手動複製到每一份副本」。實際上 owner push 一次就到位。

散佈機制是所有判準權重的地基。**地基的事實沒查清楚，上面每一層的結論都是錯的**——搞清楚後，「重複安裝會漏裝」的壓力直接消解，而「行為性變更會無聲擴散」的風險才浮現，兩者的方向完全相反。

### 把「現在不方便」誤記成「本來就該放產品端」

時機問題最容易偽裝成歸屬結論。「我們評估後認為放產品端比較好」聽起來是個架構判斷，但實際內容往往是「現在稽核不了、而且有故障在燒」。

兩者的差別在後果：前者結案，後者只是暫緩、且欠著一筆該還的提案。

### 把「我們的問題解決了」當成「這件事結案了」

產品端的迴避方案只保護自己。同一個缺陷仍然留在 lib 裡，其他產品繼續帶著，而且**他們不會從我們這裡知道**。

迴避不等於修復。走〈四種路由〉第二列時，「向上游提案」和「產品端迴避」是同一條路由的兩半，不是可選項。

## 使用方式與邊界

**這份是我們自己的判斷工具，不是要推給其他專案負責人的共同標準。** 它假設了我們的視野限制（看不到其他負責人的專案）與角色（lib 的使用端而非維護端）——這些假設對 lib owner 或其他團隊未必成立。

走完路由後，產出應該是：**一條路由結論，加上每一層的理由。** 三句話講得完。講不出某一層的理由，代表那一層還沒判斷完，不是可以跳過。

若結論是「向上游提案」，提案本身要能**獨立於這份文件成立**——lib owner 沒有義務接受我們的內部判準，他需要的是事故、風險與具體提案，不是我們的決策流程。

### 上游沒有回應時

整份路由假設上游是一個會回應的角色。若提案長期沒有進展：

- **不要因此改寫歸屬結論。**「等不到回覆」是時機問題，不是「這件事其實屬於產品端」。把它記成後者，就是〈失敗模式〉第四條。
- 產品端的迴避方案繼續用，但要留下記號（程式碼註解指向提案、或記在專案的待辦），讓它不會被當成永久設計。
- 這筆債要有地方記帳（見下）。

**目前沒有現成的記帳機制。** 提案管道是直接找 lib owner 講——對方是明確的人、溝通成本低，但**沒有留下痕跡**：沒有 issue、沒有信、沒有討論紀錄。口頭提案在雙方都忙的時候會直接蒸發，而且事後無法判斷「當初到底提了沒」。

所以記帳要記在**我們自己控制得住的地方**：

- 迴避方案的程式碼裡留註解，寫明它是暫時的、對應哪個 lib 問題
- 該次變更的 opsx change（或專案的變更紀錄）裡記下提案的內容與日期

這不是流程建議，是自保：唯一能確保這筆債不消失的人是我們自己。
